**Timing basis.** For a 4K 10-bit film with film grain, roll a 24-output window from its first to last `show=1` record, sum `busy` and the stage fields, and take the highest busy total. Records 730–765 of `s35a_film_a_r1.log` contain 12 newly shown, 12 hidden and 12 show-existing records. They sum to 911.49 ms of logged `wall`, about 912 ms, and 908.43 ms of GPU busy. The three loop-filter marks sum to 130.57 ms (14.4%). `j4k40` uses the 290 post-warm-up frames of `s35a_j4k40_r1.log`. The active mean is over frames that ran the stage, the average and share include frames that skipped it. For example, restoration averaged 1.294 ms on its 72 active frames. Dashes indicate no recorded stage time. Stage marks include intervening synchronization and lack per-shader splits. [Summary definitions](../testing/player_common/perf_stats.h#L416), [GPU timestamp attribution](../crates/rav1g/src/host/perf.rs#L497)

The 4K eight-tile film (`f33_film_b_r1.log`) had 17.20 ms GPU busy per output and 5.484 ms `inter` averaged over decoded frames. The 4K HLG run (`s35a_d2_300_r1.log`) had 9.23 ms GPU busy per output and 5.474 ms `inter` per decoded frame, with 7.57 ms mean idle gap before decoded frames. All four used the frame-wide intra schedule, the original inter dispatch paths and direct P010. They used `-nopresent`, so the 1,000 ms budget at 24 fps also has to leave room for the app's rendering.

## Shader survey

The tables cover 107 `.hlsl` entry points and 102 Rust pipelines. Names omit `.hlsl`. A `±hbd` row includes the base name and its `_hbd` variant. The timings above are shared stage totals across contributing commands. The five build-only sources and the two extra unused compound-2×2 pipelines are marked below. [Pipeline table and alias](../crates/rav1g/src/host/compute.rs#L82), [pipeline registration](../crates/rav1g/src/host/compute.rs#L332)

Savings are engineering targets in **ms per film peak window / ms per `j4k40` frame**, at the measured mix. They are separate from measured costs and represent GPU time only. Shared budgets apply once across the listed alternatives. `0 / 0` means the affected entry was off or absent in these samples. Risk rates bit-exactness, and effort ranges from a local kernel edit (low) to coordinated scheduling or layout changes (high). `6.0` also covers changes to data layout, dispatches and optimization that need no new intrinsic.

## Port order

Land and remeasure the in-flight `intra_main_hbd` change first when it is ready. There are 16,910 intra dispatches and 8,890 intra UAV barriers across 24 decoded pictures in the film's peak, around 705 and 370 per decoded picture. `j4k40` averages 189 of each on pictures with intra. The kernel port and the scheduling change both draw from the same intra timing, so rebase the scheduling target after the kernel lands.

## Shader model and device requirements

The build uses DXC `cs_6_0` with `-O3` by default and `-Od` for the two legacy main intra kernels. Shader pick also compiles every shader with `-Od` for its alternate set. The frozen FXC/Shader Model 5 line is on branch `fxc-sm5`. `-HV 2018` keeps FXC-era expression evaluation. Change evaluation order and remove old compiler workarounds one kernel at a time, especially in code that loads through root descriptors. [DXC build flags](../testing/shader_cache/shaders.py#L53)

The four logs agree on **SM 6.4**, `WaveOps=1`, lanes **64–64**, `Native16BitShaderOpsSupported=0`, and `WaveMMATier=0`. This is the observed Series app-mode D3D12 interface. The earlier console tests accepted `cs_6_0` reductions and refused native-16 and requested-wave-size PSOs. `WaveReadLaneAt(lane ^ 1)` had a recorded console failure. Microsoft's current documentation describes per-lane indexing as a legal shuffle with active source lanes. Treat the console result as a compatibility issue, validate that primitive independently before using it, and keep a group-memory path for unproven exchanges. [Console feasibility](gpu-av1-decoder.md#shader-model-6-feasibility-2026-11-12), [WaveReadLaneAt semantics](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/wavereadlaneat)

| Minimum SM | What it buys for this port | Decision |
| --- | --- | --- |
| **6.0** | Wave sums, min/max, ballots, prefix counts and broadcasts. `WaveOps` is a separate D3D12 capability. Wave operations synchronize active register values within a wave. Shared/UAV handoffs still need a suitable memory barrier. | **Keep the minimum at 6.0.** Check wave capability before making wave PSOs mandatory or retain the existing kernels as a fallback. [Wave intrinsics](https://github.com/microsoft/DirectXShaderCompiler/wiki/Wave-Intrinsics) |
| **6.2** | Native `int16_t`/`uint16_t` with `-enable-16bit-types` could reduce arithmetic or storage pressure on supporting devices. The Series logs deny the feature. `min16*` permits wider execution. Packed 32-bit loads/stores remain useful. | No floor increase. Keep exact 32-bit accumulators and demonstrate range before narrowing any intermediate. [HLSL scalar types](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx-graphics-hlsl-scalar) |
| **6.4** | `dot4add_i8packed`/`dot4add_u8packed` combine four same-signedness byte products into a 32-bit accumulator without native 16-bit support. Signed taps need a sample bias correction for unsigned pixels and special handling for tap `+128`. HBD inputs or wide intermediates need decomposition. `dot2add` is floating-point and requires the low-precision feature. | Optional experiment on an exact 8-bit kernel, gated on PSO creation and measured wins. Profile support alone establishes neither instruction throughput nor net gain. [SM 6.4 intrinsics](https://github.com/microsoft/DirectXShaderCompiler/wiki/Shader-Model-6.4#packed-dot-product-intrinsics) |
| **6.5+** | `WaveMatch`/`WaveMultiPrefix*` can group equal list keys. Wave matrix is a separate capability, with no exposed tier here. Fixed-point AV1 butterflies also round and clamp between steps. | Defer these features on the observed device. [SM 6.5](https://microsoft.github.io/DirectX-Specs/d3d/HLSL_ShaderModel6_5.html), [Wave Matrix capability](https://microsoft.github.io/DirectX-Specs/d3d/HLSL_SM_6_x_WaveMatrix.html) |
| **6.6** | `[WaveSize(n)]` can pin a supported width. Pack/unpack helpers and compute quad mapping guarantees also arrive here. | The device tops out at 6.4. Design wave paths for wave32 and wave64 and keep a shared fallback for other widths such as WARP's tested wave4. [WaveSize](https://microsoft.github.io/DirectX-Specs/d3d/HLSL_SM_6_6_WaveSize.html), [Compute quad mapping](https://microsoft.github.io/DirectX-Specs/d3d/HLSL_SM_6_6_Derivatives.html) |

Keep wave participants active with neutral values for tail lanes. Form logical blocks explicitly, then combine partials across waves through shared memory. `SV_GroupIndex / WaveGetLaneCount()` alone cannot establish wave membership. A group sync must be reached uniformly and a cross-group dependency still needs dispatch-level ordering. When a fused pass reads another lane's UAV store, either keep the value in registers/shared memory or use device-memory ordering. [Group and wave indexing](https://microsoft.github.io/hlsl-specs/proposals/0048-group-wave-index/), [Device-memory group sync](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/devicememorybarrierwithgroupsync)

Any **required** profile above 6.0 raises the check reached by `rav1g_device_create`, through `Device::with_d3d12` and `CheckFeatureSupport(D3D12_FEATURE_SHADER_MODEL)`. It also changes the DXC cache/profile and the build's `shader_set.txt` validation. An optional higher-profile PSO needs capability-based selection before pipeline creation and a `cs_6_0` fallback. Decide on a 6.4 floor only if a measured gain across target Series devices is worth the compatibility cost. A second owner decision is whether to keep experimental controls and unused entries once the live paths are ported.
